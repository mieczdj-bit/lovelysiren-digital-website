# Pass008 retention and deletion-runtime recommendations

All recommendations require Executive Producer/legal/operational approval. No statutory duration is invented and no live decision or deletion is made. The emulator fixtures' review dates are synthetic test inputs, not policy. References: Pass004 retention-and-cleanup.md; Pass007 operator-procedure.md; account-lifecycle-deletion-008.md.

| Category | Minimum proposed retained data / action | Purpose and review/removal decision |
|---|---|---|
| Permanent mappings | Current development path retains only UID↔canonical-ID mapping and minimal claim, under explicit retain-minimal approval | Non-reassignment and ownership reconciliation. Both UID and mapping remain personal/linkable; not anonymous or justified forever by “permanent.” Approve necessary duration/review criterion and future keyed tombstone design before live use; no automatic purge yet |
| Deleted marker | UID, canonical ID, state/revision, operation ID and closure/update times; remove profile name/phone/eligibility/grant hash | Prevent stale re-enrollment/reactivation and support verified closure. Review linkage necessity alongside identity retention; never restore deleted automatically |
| Policy/Terms evidence | Reviewed choice erase OR keep only version identifiers, source hashes and server acceptance times; no profile contact fields | Necessary agreement/dispute evidence only, with approved minimum fields, holds and review/removal criterion. Retaining evidence is not retaining an active account |
| Reservations/invitations/grants | Remove UID-bound reservations, grants and associated invitations under reviewed erase choice | No reissue/retry need after irreversible closure; reject conflicting ownership. Prevent stale retries through retained deleted marker. Incomplete provisioning must first be reconciled, even after capability expiry |
| Security records | Remove unnecessary per-account lifecycle event history; retain only reviewed, expiring security counters and necessary operational audit evidence | Existing bounded temporary cleanup handles expiry separately. Logs/sinks/access, remaining counters and incident holds require actual operator inventory. Expiration is not physical deletion; no new scheduler/purge guarantee |
| Support requests | Restrict access, remove unnecessary sensitive attachments/content after case resolution under approved review criteria; keep only necessary case references/hold evidence | The foundation records retain-under-reviewed-policy; it does not erase Gmail. Actual mailbox verification/retention handling is still required |
| Transaction references | Remain product-owned; company operation keeps only necessary verified receipt/inventory references | RTA decides transaction obligations, eligibility and retention. No raw purchase token/order IDs enter company operation. Do not assume deletion forfeits purchases or that product absence was proven |
| Deletion operation | Minimal owner/scope/authorization/step/result/review/failure evidence; no email, password, DOB or arbitrary error strings. Last20 failures retained; attempts/truncation explicit | Idempotency, partial-failure recovery and completion evidence. Review completed-operation owner linkage, legal purpose and eventual minimization/purge. No indefinite log retention or autonomous purge is implemented |

The worker accepts only explicit reviewed decisions for all eight categories, an opaque approval reference, a future reviewAt and hold none/active. Missing/malformed/expired approval or active hold blocks erasure. ReviewAt is a mandatory reassessment deadline, not a statutory retention period or automatic deletion time. Prior retention reviews remain in the private operation. After cleanup, decisions cannot switch categories; an authorized identical-category review can extend/reassess reviewAt. Active worker leases lock review updates; urgent hold/cancellation during an external call needs a separate design before production. Retained external records require honest scope in completion/support replies.

## Separate runtime and authorization

The current registration runtime must NOT gain broad Auth update/delete rights. New coordinator is absent from Functions exports and the account-only staging package; no frontend or Admin credentials are added. The normal APIs import lifecycle guards only. No cloud service account or permission is created.

Future deletion deployment needs a separately approved principal and authenticated operator/worker boundary, with explicit deletion request/review/execute/inspect permissions. Do not reuse the Pass006 RTA lookup allowlist as deletion authority. Consider independent approval/review roles rather than one actor doing every step; production separation-of-duties enforcement is not implemented by local fixtures.

Candidate permissions to evaluate, not grants: firebaseauth.users.get, firebaseauth.users.update (disable/revoke), firebaseauth.users.delete; and firebasedatabase.instances.get/update for the company state/operation store. Platform invocation/deployer actAs needs independent review. No Owner/Editor, hash-config access, Auth provider/config update, product SQL access, key download or broad project automation is proposed. These APIs may expose shared-project privileges beyond one namespace/UID, so IAM alone does not guarantee safe isolation. Review storage separation, server-side path guards and authoritative product fencing before any live permission change. Do not silently broaden permissions on failure.

## Remaining blockers to real closure

1. Approve retention purposes, minimum fields, review/removal criteria, holds, external support/log/backup handling and accountable review monitoring.
2. Implement and authenticate comprehensive product inventory/fencing. RTA inventory/deletion and legacy binding are absent; company-side missing links are not proof of no game data.
3. Review cancellation/urgent holds, Auth generation/CAS limitations, direct Firebase client delete/link behavior and prohibition on UID reuse. Disabling a Firebase user cannot be undone through the current owner-reauth-only transition method; a separately authorized admin recovery procedure is still needed.
4. Review production worker auth, least privilege, execution budget/timeouts, retry/dead-letter scheduling, bounded namespace/operation size, read contention, provider failures and independent completion evidence.
5. Validate Node22, retain all prior Privacy/billing/API/Hosting/provider/domain/activation gates, and separately authorize any controlled staging. New source has no production-enable route.

A company-only real test is still NOT READY for closure. The local successful path uses explicit synthetic inventory/receipt/retention fixtures. It does not approve manual production cleanup or substitute for RTA's trusted service. No source or data from RTA was modified or directly accessed by the coordinator.
