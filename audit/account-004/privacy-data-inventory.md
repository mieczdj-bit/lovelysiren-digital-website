## Operational distinction and access model

PUBLIC NOW means the static production website. DEVELOPMENT means implementation exists but account feature flags are off on the public site; only isolated synthetic local emulator tests run it. PROVIDER/UNVERIFIED means supplier processing or settings require cloud/operator inspection; source alone cannot establish operational log retention, IAM or an installed SDK's actual network behavior.

For DEVELOPMENT account records, application access is restricted to the trusted backend and authorized operators with privileged Firebase permissions. An eligible verified user can read only the allowlisted own-profile view. RTDB client access to the private namespace is denied by the proposed/local rules. This is not a claim those rules are deployed. Firebase Admin privileges bypass client rules; privileged access and inherited live parent rules must be verified separately.

## Mismatches and corrections

1. PUBLICATION: main/public still October 5 combined policy; full account draft was never published. Retain old disclosures. Correct historical references with this audit and explicit draft status; no silent overwrite.
2. WEBSITE SCOPE: old policy lacks most website account categories above. Full replacement draft remains approval-only. 004 adds incomplete registrations/reservations, actual login-attempt handling and no custom login history, and concrete browser-storage distinctions.
3. RETENTION: expiry previously permitted physical cleanup but the bulk deletion could race a renewed invitation/counter. Fixed with bounded per-record transactions that recheck expiry; safe retry/idempotency is tested. No schedule activated. Durable identity/profile/history/reservation and external log/backup deletion remain operational/legal decisions.
4. REGISTRATION CONTROLS: preparation checked registrationEnabled, but an already issued grant could still reach provision/completion after that flag was switched off. Both now enforce the registration gate as well as service mode/gate. Capability checks also reject missing or nonnumeric expiry metadata; malformed records are never treated as nonexpiring authorization. Real Auth creation through direct provider APIs remains separate from company profile/ID authorization.
5. POLICY DATES: reject normalized invalid calendar dates such as February 31, not only unparseable/future values. Client can safely identify the already published Terms while privacy version/approval stay unset. Offline reviewed control template pins actual Terms ID/date/source hash and leaves every activation gate off.
6. RTA SEPARATION: the old combined policy is the only current in-game target. A separate code-based privacy draft is now available for review; no game file or public link changed.
7. RTA LAUNCH CLAIMS: native rewarded-ad code exists and requests child-directed/under-consent/general/nonpersonalized settings; banner component is a preview, billing adapter is not live and content entitlement enforcement is false. No complete game age/DOB-screen implementation was found in the reviewed gameplay code. Those facts block treating planned release promises as proven implementation. The presence of privacy flags is not a complete child-privacy or Play compliance assessment.
8. NOTIFICATIONS/DELETION: real mail delivery and verified manual deletion handling are untested; no automatic deletion or global-session management UI is represented as working. End-to-end closure before RTA release is still a critical dependency.
