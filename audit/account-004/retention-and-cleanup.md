## Cleanup implementation and limits

`functions/src/maintenance.js` remains server-only and dry-run by default. It queries only four fixed groups within `lovelySirenAccountsV1`: registrationGrants, linkGrants, throttles, testInvitations. Default limit is 100 candidates per group (at most 400 total); hard maximum is 500 per group. Invalid time, limit or dry-run type is rejected. Queries use the existing expiresAt indexes.

Applied cleanup now rechecks each current record inside a transaction. A renewed counter/invitation with a future expiry is skipped, even if the earlier query found it expired. A disappeared record is skipped. Partial failure surfaces an error; retrying safely skips already removed records and removes remaining eligible ones. Permanent namespace paths and RTA/purchase paths cannot be selected through caller input. Dry-run reports candidates and performs no writes.

Proposed operation: an authorized operator runs a dry-run then an explicitly reviewed apply after the first test and at hourly intervals during a controlled test window. Later, a dedicated reviewed scheduler could run the same bounded batches with minimal service identity, monitoring, batch cap and retry/backoff. No scheduler function, cloud trigger or live cleanup is deployed by this pass. A failed/late job may delay physical deletion; capability validation still rejects expiry immediately.

Backlog monitoring should use group counts and failure counts only, not dump profile payloads. Investigate repeated failures before increasing limits. Never “solve” a backlog by removing the whole namespace, rules, Auth users or game database.

Tests cover dry-run, bounds, idempotency, injected partial failure/retry, renewal races, malformed/missing expiry and preservation of identity/profile/history/reservations/control/game/purchase sentinels. Actual emulator results and any limitations are in the completion report.
